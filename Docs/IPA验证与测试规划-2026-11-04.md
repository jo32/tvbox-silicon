# IPA 验证与全量测试规划

目标：一个装到手机上的包，怎么系统地证明它「是完整的、能装的、该有的都有、不该错的都没错」。
分四层：静态验证 → 装机验证 → 全量功能 → UI 自动化。每层都能单独跑，也能串成一条发版流水线。

---

## 一、静态验证（不装就能查，30 秒）

对着 `.app`（或解开 `.ipa` 的 `Payload/xxx.app`）跑这几条，任何一条不过就不用往下走：

```sh
APP=TVBox-iOS.app

# 1 签名是否自洽、有没有被改过
codesign --verify --deep --strict --verbose=4 "$APP"

# 2 谁签的、团队、bundle id、是否带调试权限
codesign -dv --entitlements :- "$APP"

# 3 描述文件：有效期、设备白名单、app id、get-task-allow
security cms -D -i "$APP/embedded.mobileprovision" > /tmp/pp.plist
/usr/libexec/PlistBuddy -c "Print :ExpirationDate" -c "Print :ProvisionedDevices" \
  -c "Print :Entitlements:application-identifier" /tmp/pp.plist

# 4 是不是真机包（模拟器包改后缀装不上）
/usr/libexec/PlistBuddy -c "Print :CFBundleSupportedPlatforms" "$APP/Info.plist"

# 5 有没有被塞进来的动态库（注入检测）
otool -L "$APP/TVBox-iOS" | grep -vE "^\s*(/usr/lib|/System|@rpath)" | head

# 6 崩溃符号化要对得上：可执行文件 UUID ↔ dSYM UUID
dwarfdump -u "$APP/TVBox-iOS"
dwarfdump -u TVBox-iOS.app.dSYM
```

对应的自动化判据（适合写成脚本 / 让 AI 判读）：

| 检查 | 通过标准 |
|---|---|
| 签名 | `codesign --verify` 无输出且返回 0 |
| 团队与 app id | `TeamIdentifier` 与描述文件 `application-identifier` 前缀一致 |
| 目标设备 | 待装设备的 UDID ∈ `ProvisionedDevices`（企业签名则允许全量） |
| 平台 | `CFBundleSupportedPlatforms` 含 `iPhoneOS` |
| 时效 | `ExpirationDate` 在测试窗口内 |
| 体积 | 与上一次发版同配置相差 < 5%（突然变大要看是不是误打进资源） |
| 注入 | 第 5 条除 `@rpath` 自带的 Frameworks 外无外部 dylib |

> 注：`otool -L` 的 `@rpath` 项要接着查 `Frameworks/` 是否真有对应文件，`@rpath` 只是变量，
> 不代表干净。Apple 自己也提醒不要对代码签名块的结构做硬编码假设，用 `codesign` 判断，
> 不要自己解析 `_CodeSignature`。

## 二、装机验证（证明「能装上、能起来、没崩」）

```sh
xcrun devicectl device install app --device <UDID> <path>/TVBox-iOS.app
xcrun devicectl device process launch --device <UDID> --console wda.prdc.yingxia.dev
```

判据：

1. `install` 返回 0；`launch` 打印的 PID 在 3 秒后仍存活（`devicectl device info processes`）。
2. 控制台无 `Fatal error` / `EXC_CRASH` / `dyld: Library not loaded`。
3. 首启 10 秒内出首屏（不是无限 loading）—— 二开里最容易在这里翻车的是启动期同步逻辑
   （`seedAggregatedSubscriptions`、`restoreSubscription`）。
4. 冷启 → 杀进程 → 热启各一次，状态不丢（订阅、收藏、播放进度）。
5. 覆盖安装（旧包 → 新包）不丢数据；这是二开「聚合源」和「保险箱」最容易出问题的地方。

## 三、全量功能测试（手工 / 半自动）

按「页面 × 平台 × 网络」三轴铺开。本仓库有现成的 DEBUG 启动钩子，可以把每个页面直接打开截图，
不用一路点进去：

```sh
xcrun simctl launch <device> wda.prdc.yingxia.dev -qaSection settings -qaPage resource-order
xcrun simctl io <device> screenshot /tmp/qa-resource-order.png
```

可用 `-qaPage` 直达的页面（`App/QALaunch.swift`）：`vault`、`privacy`、`playback`、`runtime`、
`logs`、`cache`、`resource-order`、`segment-sources`、`speech-subtitles`、`site:<key>`、
`detail:<key>:<vod_id>`、`channels:<i>` 等。

必测矩阵（每项至少 iPhone + iPad 各一遍，iCloud/同步相关加 Mac）：

| 模块 | 关键点 | 最容易漏的失败 |
|---|---|---|
| 订阅 | 导入 / 刷新 / 删除 / 多仓 / 覆盖安装 | 删掉的聚合源被启动逻辑加回来 |
| 点播源 | 列表、分组、拖拽改派、折叠记忆 | 刷新后改派丢失 |
| 测速 | 全量测绘、停止、结果排序 | 排序只按分辨率生效 |
| 播放 | 直连 / 中转 / HLS 重封装 / 外挂字幕 / 语音字幕 | 防盗链源在识别阶段 403 |
| 跳片头片尾 | 手动标记、章节、悬浮按钮倒计时 | 片尾标记算不出来 |
| 保险箱 | 设密码、隐藏订阅/源、切后台上锁、遮罩 | 缩略图露出内容 |
| 多环境 | 新建、切换、删除、上报开关 | 切换后历史没分区 |
| 折叠屏 | 折叠/展开切换方向、全屏 | 方向锁状态残留 |
| 同步 | iCloud 开关、冲突合并 | 覆盖安装后重复条目 |

网络条件必须掺进来（真机拔网、弱网、机房封 IP 的源），模拟器永远测不出来。

## 四、UI 自动化规划

### 选型（结论先给）

| 层 | 工具 | 理由 |
|---|---|---|
| 单元 / 逻辑 | Swift Testing（仓库已有 592 项） | 秒级，PR 必跑 |
| iOS UI 主流程 | **XCUITest**（仓库已有 `UITests/`） | 一等公民、可跑真机、无外部依赖，约 2 倍于 Appium 的速度 |
| 跨端冒烟 / 多语言多机型扫 | **Maestro**（YAML） | 十分钟能写出十条流程，适合扫「每个页面能不能打开」 |
| 跨端深度（真需要再说） | Appium | 只有在还要覆盖 Android 时才有意义；iOS 26 上 WDA 端口绑定还有坑 |

不建议一上来就 Appium：本仓只有 iOS/macOS/tvOS，跨端收益为零，而 WDA 的维护成本全要自己吃。

### 用例怎么写才不 flaky

1. 每个可点控件补 `accessibilityIdentifier`（本仓已有 `sources.probeAll`、`sources.sortByFix`、
   `player.options`、`qa.open-detail` 这类命名，沿用 `<页面>.<控件>` 的格式即可）。
2. 禁止 `sleep`，一律 `waitForExistence(timeout:)`；进入用例前 `setUp` 重置状态
   （本仓可用 `-qaIsolatedData 1` 把数据写到独立文件）。
3. 断言分层：结构断言（元素存在）→ 文案断言（L10n key 对应四种语言，至少跑中文 + 英文）→
   截图基线（只在固定模拟器型号 + 固定系统版本上比，避免像素噪声）。
4. 一个用例只测一件事；登录、订阅导入这类前置抽成 `XCTestCase` 的 extension 复用。

### 建议的第一批（按性价比排序）

**XCUITest 主流程 8 条**（跑在 PR 上，目标 5 分钟内）

1. 冷启动到「现在观看」出首屏，且没有错误横幅。
2. 设置 → 播放内容 → 选片资源排序：拖动一行，杀掉进程再进，顺序还在。
3. 设置 → 片段标记来源：三条公开时间戳的开关是禁用的（回归本轮修复）。
4. 设置 → 语音字幕：列出语言、只能选一个、重进仍选中。
5. 保险箱：设密码 → 隐藏一个源 → 回列表该源消失 → 解锁后回来。
6. 保险箱：隐藏后切后台再回前台，需要重新解锁。
7. 点播源：拖一个子源到另一个订阅下，刷新订阅后仍在。
8. 删除一个聚合订阅 → 冷启动 → 它不回来（回归本轮修复）。

**Maestro 冒烟 10 条**：每个 tab 打开一次、每个设置子页打开一次、播放页开关一次。
YAML 短、可读，适合交给非开发同学加页面。

### AI 能做什么、不能做什么

* 能做：把无障碍树 + 截图喂给模型，自动生成 Maestro/XCUITest 草稿；定位符失效时按文本/结构
  自愈；批量出「每个页面打开后的截图」，人只看异常的那几张；按改动文件推断该跑哪几条用例。
* 不能做：替人判断「这个交互对不对」。本次审计里 #2、#5 这类问题（开关存在但底下没数据）只有
  读过代码、知道数据从哪来才看得出来，截图全绿。

本仓库已经把前半段做出来了：`QALaunch` 的页面直达 + `simctl` 截图，就是「AI 批量出图 → 人看
异常」的那条流水线，只是还缺一个 diff 基线。补法：把每页截图存进 `Fixtures/qa-baseline/<page>.png`，
回归时用 `sips`/`compare` 出差异图，只报告差异超过阈值的页面。

## 五、落地顺序（建议）

1. **本周**：把上面 8 条 XCUITest 写出来（`UITests/OnboardingUITests.swift` + `SettingsUITests.swift`），
   跑在 PR；给 `-qaPage` 的每个页面补一张基线截图。
2. **下周**：Maestro 冒烟跑通一台真机（`maestro test flows/`），把「装机 + 冒烟」合成一个脚本
   （`Scripts/install-and-smoke.sh`：build → install → launch → 10 条 YAML → 出报告）。
3. **之后**：把静态验证那 7 条判据写成 `Scripts/verify-ipa.sh`，发版前必跑；CI 上接 Xcode Cloud
   或 GitHub Actions（macOS runner）跑单元 + 主流程。
